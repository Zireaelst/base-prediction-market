## Product decision

Explore has two interoperable views: **Swipe** for mobile-first single-question discovery and **List** for scanning, search, and comparison. Both share category state and real venue data. Right selects the first outcome and left selects the second; a visible Skip control advances without recording. Selection opens a confirmation form; no gesture alone persists a forecast or creates a paper position. The default forecast destination is an automatically created, owner-only personal space; the user can instead explicitly select a room they have joined. Posting to a public room is never implicit.

The advantage is not exchange liquidity or generic play-money questions. It is a repeatable learning loop: choose a real question, estimate its probability and explain why, see revisions and later resolution-calibrated results, and optionally discuss in a permitted room. Market prices can be revealed on the swipe card; they remain visible in List and detail. Do not describe concealment as scientifically validated debiasing. Future separate experiments: weekly curated room picks, post-resolution reflection, consent-aware room distributions. Do not implement those experiments in this scope.

## Discovery and venue adapter

- The server obtains public category navigation, resolves allowlisted category paths to market pages, and fetches each page with venue pagination. Use stable internal category keys `crypto`, `sport`, `esports`, `finance`, `politics`, and `all`; resolve provider page IDs by path, not hardcoded observed UUIDs. Only supported paths are accepted; unrecognized categories fail clearly. Never use category labels or numeric category counts as substitutes for page membership.
- `all` interleaves eligible pages deterministically with a bounded per-category fetch so short-lived crypto markets cannot monopolize its first page. Maintain stable pagination/deduplication and truthful exhaustion/loaded counts; if one category is empty or fails, label the degraded source and continue only with genuinely fetched results. A category page itself loads the corresponding source page, not a filter over currently loaded All items. No fake fallback records.
- Add a conservative provider category to the normalized `Market` contract. For single markets, preserve original venue market ID, slug, pair of outcome token IDs, outcome labels from official provider metadata when present, resolution terms without changing their meaning, deadline, source, observation timestamp, and terms version. Prefer explicit two-label metadata; for semantically clear binary questions use truthful Yes/No or Up/Down. Ambiguous labels, unavailable identity/terms, and provider group records must not enter swipe or forecast selection. They may be omitted from this binary-only catalog with an honest count of eligible results; no invented outcome-to-token mapping.
- Existing market detail URL remains stable. Read-only detail/list still show venue probability with a descriptive non-executable label; swipe reveals it on request. Distinguish stale cache (render with observation time, no submit), empty legitimate category, malformed/unsupported source records, total provider outage, and retry. Re-fetch the selected market on POST; the server verifies outcome ID, freshness, terms, status, authorization, and lock time rather than trusting a card snapshot.

## Personal forecasts and authorization

- Add a distinct private `personal` room kind to existing rooms storage, defaulting existing/new normal rooms to `shared`. Enforce at most one personal room per owner with a database uniqueness constraint, create it atomically on first personal forecast, and assign only its owner as member. Existing shared-room operations must not join, invite, enumerate as public rooms, or reveal personal rooms to other users. Owner activity/profile exposes their personal forecasts; public profiles and room directory do not. The room picker lists only rooms in which the user is already a member and excludes personal rooms from shared choices.
- Expose one authenticated forecast-creation path accepting venue slug, outcome ID, user-entered outcome probability (0–100%), nonempty rationale, and explicit destination (`personal` default or a joined room ID). Migrate the existing room form to this path and remove the obsolete room-specific creation route; room access remains server-enforced. Reuse the existing `addForecast` validation, revision history, lock, score recalculation, and identity checks; do not duplicate forecasting rules in UI or add a direction-only scored record. If the same market was forecast in the same destination, show the existing forecast and link to revision instead of silently overwriting it. A personal entry and a separately chosen shared-room entry are distinct records and visibly labeled.
- Preserve inputs across auth prompts, fetch failures, or recoverable errors. An interrupted or ambiguous submit must not be represented as confirmed; re-read the relevant destination before allowing another attempt. A completed forecast appears in activity and the owner profile, including correction/last-known score states. Personal scores use the same resolution logic as room forecasts.

## Interaction and visual design

- Keep the existing black/off-white/lavender, Geist Pixel headings, Geist Sans UI, Geist Mono metadata, original ASCII/dither identity. Deck has one readable card, question, verified outcome labels, closing time, resolution source (or explicitly unavailable), venue/source freshness, category, market detail link, and an optional odds reveal. Decorative effects never overlap prices or controls. No global scroll lock.
- Both touch and pointer gestures have a short threshold and clear cancellation; vertical page scrolling remains native. Outcome-labeled left/right buttons, a separate Skip button, accessible names and focus order provide complete keyboard/non-gesture paths. No auto-advance on a failed submission. Respect `prefers-reduced-motion`, with a static transition fallback. The card adjusts at 320px and large screens without clipped question text or horizontal overflow.
- Confirmation shows selected real outcome label/token meaning, probability input without an invented default conviction, rationale, chosen destination, terms/source/deadline/freshness, and an explicit free-forecast button. Focus enters the form, Escape/cancel returns to the card, and success returns focus to the next card. Login required only when recording, not for read-only exploration. Room access changes or expired markets fail with actionable messages and preserved drafts.
- Empty category, end of deck, loading next venue page, stale snapshot, provider outage, nonmember room, locked/resolved market, and unrecognized binary mapping have distinct labels and recovery. Existing clearly labeled paper simulation remains on market detail and is not connected to swipe.

## Scope boundary

This is one product-focused implementation with ordered venue, persistence, and UI work; defer new recommendation algorithms, multi-outcome/group prediction UI, private social aggregate disclosure, streaks, push notifications, real venue execution, and new blockchain contracts. Unsupported venue capabilities stay explicit. AXON imagery is only directional; no attachment was available for exact visual comparison and no fidelity claim is made.
